# v1.0.1 — Bars stopped falling at 15 in the web app, and the sad ending was unreachable

Reported from the phone: in the web app the four bars never went below 15,
however long the creature went uncared for. Chasing it turned up three
separate faults stacked on top of each other, all of which had to go before
the runaway ending could happen at all.

## Fixed

- **The web app never saved what happened while you were playing.**
  Everything `Pet::tick()` accrues — the per-minute decay, care mistakes,
  the neglect run — lives in the C++ object and reaches storage only when
  `Pet::save()` runs. `tick()` just raises a pending flag and leaves the
  writing to `flushSave()`, which the firmware calls from `loop()` and the
  iOS app calls after each update; this build called neither, so storage was
  written only as a side effect of the five-minute clock resync.

  On iOS that omission is invisible — backgrounding suspends the process,
  the creature survives in memory, and nothing re-reads storage. In a
  browser, closing the app destroys the whole module and the next launch
  loads from IndexedDB. So **any session shorter than five minutes had its
  entire decay thrown away**, and the value that came back was the last one
  the resync wrote — one that had just been through the offline catch-up's
  floor of 15. Hence bars parked at exactly 15 for ever.

  The save export now flushes the live creature into storage first.

- **The creature aged at twice the intended rate while the app was open.**
  Same root cause, other end: the five-minute resync re-walked minutes the
  live tick had already applied. Measured at 960 game minutes per 480 real
  ones. This one affected **the iPhone app too**, since both drive the same
  resync; the same fix clears it, because marking the state current stops
  the resync re-walking anything.

- **The runaway ending could not be reached in the web app.** Two reasons
  beyond the above. The neglect counter was never saved, so closing the app
  reset it — on hardware that just means "a reboot forgives you", but a
  closed web app is destroyed every time. And the counter only advanced
  while the app was on screen, so the ending's real condition had become
  *an hour of holding the app open watching a creature you refuse to feed*.

  The counter is now saved, and it advances while the app is shut as well.
  Arming the ending used to want 78–108 minutes of screen time; it now wants
  17–29, spread across as many short visits as you like, with the final hour
  passing on the wall clock the way it does on the original hardware.

## What has not changed

**Time you spend away still cannot hurt your creature.** The offline
catch-up keeps its mercy floor: bars left alone stop at 15 and never reach
zero by themselves, so the neglect run cannot even begin until all four are
already flat — which takes repeated visits that fed it nothing. A fortnight
away and one visit still finds it hungry at 15 with the counter at zero. A
creature put to sleep is untouched by any of this.

In other words the rule is now *neglect*, not *absence*: what counts is time
you were there and chose not to care.

## Under the hood

The vendored fork picks up two more deliberate local changes (four in
total), both written up in `upstream-expanded/README.md`: the neglect
counter is persisted, and it accrues during offline catch-up. Saves stay
compatible in both directions — an older save simply starts the counter at
zero, and an unmodified build ignores the extra key.

# v1.0.1 — 웹앱에서 바가 15에서 멈추던 문제, 그리고 슬픈 엔딩이 불가능하던 문제

폰에서 제보: 웹앱에서 아무리 돌보지 않아도 네 바가 15 아래로 내려가지
않는다. 추적해보니 서로 겹쳐 있는 결함 세 개가 나왔고, 도망 엔딩이
성립하려면 셋 다 고쳐야 했습니다.

## 수정

- **웹앱이 플레이 중에 일어난 일을 저장하지 않았습니다.**
  `Pet::tick()`이 쌓는 것 — 분당 감소, 돌봄 실수, 방치 카운터 — 은 전부
  C++ 객체 안에만 있고, `Pet::save()`가 돌아야 저장소에 닿습니다.
  `tick()`은 플래그만 세우고 실제 쓰기는 `flushSave()`에 맡기는데, 펌웨어는
  `loop()`에서, iOS 앱은 업데이트 직후에 이걸 부르지만 **이 빌드는 둘 다
  부르지 않았습니다.** 그래서 저장소는 5분 주기 시계 재동기화의 부수
  효과로만 갱신됐습니다.

  iOS에서는 이 누락이 드러나지 않습니다 — 백그라운드로 가도 프로세스가
  정지될 뿐이라 객체가 메모리에 살아 있고, 저장소를 다시 읽지 않습니다.
  브라우저는 앱을 닫으면 모듈이 통째로 파괴되고 다음 실행 때 IndexedDB에서
  읽습니다. 그래서 **5분보다 짧은 세션은 그동안의 감소가 통째로 버려졌고**,
  돌아오는 값은 재동기화가 마지막으로 쓴 값 — 즉 방금 오프라인 보정의
  하한 15를 거친 값이었습니다. 바가 정확히 15에 박혀 있던 이유입니다.

  이제 세이브를 내보내기 전에 살아 있는 상태를 저장소로 밀어넣습니다.

- **앱을 켜두면 나이가 두 배로 갔습니다.** 같은 원인의 반대편입니다.
  5분 주기 재동기화가 라이브 틱이 이미 처리한 시간을 다시 걸었습니다.
  실측 480분에 게임 내 960분. 이건 **아이폰 앱도 마찬가지**였습니다 —
  같은 재동기화를 쓰기 때문입니다. "여기까지 반영됨"을 기록하게 되면서
  같은 수정으로 함께 해결됐습니다.

- **웹앱에서 도망 엔딩에 도달할 수 없었습니다.** 위의 것들 외에 두 가지
  이유가 더 있었습니다. 방치 카운터가 저장되지 않아 앱을 닫으면 0으로
  리셋됐습니다 — 하드웨어에서는 "재부팅하면 용서받는다" 정도지만, 웹앱은
  닫을 때마다 파괴됩니다. 그리고 카운터가 화면에 켜져 있을 때만
  올라가서, 엔딩의 실제 조건이 *밥을 안 줄 작정으로 한 시간 동안 앱을
  켜놓고 쳐다보기*가 되어 있었습니다.

  이제 카운터가 저장되고, 앱을 닫아둔 동안에도 올라갑니다. 엔딩까지
  필요한 화면 시간이 78~108분에서 **17~29분**으로 줄었고, 짧은 방문
  여러 번으로 나눠 채울 수 있으며, 마지막 한 시간은 원본 하드웨어처럼
  벽시계로 흘러갑니다.

## 바뀌지 않은 것

**자리를 비운 시간은 여전히 포켓몬을 해치지 못합니다.** 오프라인 보정의
관용적 하한은 그대로입니다. 그냥 두면 바는 15에서 멈추고 스스로 0에
닿지 않으므로, 네 바가 이미 모두 0이 되기 전에는 방치 카운트가 시작조차
하지 않습니다. 그리고 0으로 만들려면 아무것도 먹이지 않은 방문을 여러 번
반복해야 합니다. 2주 비웠다가 한 번 열어봐도 배고픈 상태(15)에 카운터는
0입니다. 재워둔 포켓몬은 이 전부와 무관합니다.

정리하면 규칙이 *부재*가 아니라 *무시*가 되었습니다. 세는 것은 곁에
있으면서 돌보지 않기로 한 시간입니다.

## 내부 변경

포크에 대한 의도적 로컬 수정이 둘 더 늘어 총 네 개가 되었고, 각각의 근거는
`upstream-expanded/README.md`에 적어두었습니다. 방치 카운터를 저장하는
것과, 오프라인 보정 중에도 누적되게 하는 것입니다. 세이브 호환성은
양방향으로 유지됩니다 — 이전 세이브는 카운터가 0에서 시작하고, 수정되지
않은 빌드는 추가된 키를 무시합니다.
